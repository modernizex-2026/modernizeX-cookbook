Uncovered Code — Root-cause Analysis

Technical assessment: Uncovered methods are classified into 4 groups (A, B, D, C) by their technical nature, separating genuinely untested business logic from branches that carry no business logic.
Group A  — Framework Entry & Abort Paths
Batch-framework entry points and infrastructure error branches

mainProcess() is the entry point invoked by BatchServiceBase.execute() at batch runtime. Unit tests call each business method directly — skipping this entry point by design.

abort*(), setCompletionCode(), getFileSet() are abnormal-exit branches (I/O error, DB error) that cannot be reproduced at the unit-test layer.

Group B  — Core Business Flow
Business-loop bodies that require simultaneously matching rows across several master tables

Data validation, master updates, pricing/cost calculation, stock movements... only execute when at least one input record matches across several master tables at once.

Preparing such multi-table datasets is beyond the unit-test design scope — these paths are verified at the system/integration test layer.

Group D  — Auto-generated DAO Wrappers
Generated data-access layer — no business logic

readX(), writeX(), deleteX(), rewriteX(), startXAtKey(), openXFile() are thin auto-generated wrappers derived from the COBOL FD/SELECT declarations. Each is 3–5 delegate lines — no business logic.

Just as JPA's repository.findById() needs no dedicated unit test: a misconfigured wrapper fails every test that calls it, which is detection enough.

Group C  — Interactive Terminal
Terminal input flows — not simulatable in unit tests

accept*(), open*Window(), prompt*() come from COBOL ACCEPT FROM TERMINAL / DISPLAY — blocking reads from a real terminal.

Unit tests cannot simulate keyboard input without a full terminal emulator. Verified via screen tests / manual acceptance tests.
