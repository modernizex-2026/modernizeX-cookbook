## メッセージコード体系について（重要・観点導出の前提）

本システムには **EI/EF/GF 等のメッセージコード体系が無い**（§3 の「Message ID」列は全行 `-`）。
`msg_codes.py MENU00.xml` = **0 codes / 0 raises**（MS0010 ほかも 0）。各画面は英語のメッセージ
文言を画面下部のメッセージ行に**直接表示**する（種別 E=エラー／W=警告／C=確認）。

→ 導出上の帰結：
- 異常系 TC の判定（期待結果）は、msg コードではなく **画面上の逐語メッセージ「…」** を用いる。
- 「1 メッセージコードあたり 1 異常系 TC」という密度ルールは、本アプリでは **§3 の各エラー行
  （E／一部 W）＝ 1 個の distinct トリガー点** に読み替える。§3 の E 行を過不足なく TC 化した。
- I/O 記帳失敗（`… write failed`／`Update failed`／`Delete failed`／`… update failed`）は
  **環境障害クラス（EF 相当）**。マスタ保守画面では代表 1 件（「回復・リラン」）に集約、取引画面では
  §3 に列挙された各記帳段階（採番失敗・ヘッダ記帳失敗・元帳記帳失敗・残高更新失敗…）を個別 TC 化した
  （前提条件に `*(要実データ：I/O 障害環境)*` を明記）。

## 監査結果（audit_testcase.py --reg <REG> --root MENU00）

`# 356 CANDIDATE finding(s)` — 内訳と根拠付け（すべて解決済み）:

1. **`[vague]` ×355** — 「異常系 case but expected cites no message code / STOP」。
   → **棄却（意図どおり）**。本アプリは EI/EF/GF のメッセージコード体系を持たず（`msg_codes`＝0 codes）、
   異常系の判定は画面上の逐語英語メッセージ「…」で行う設計。監査正規表現 `[A-Z]{2}\d{3}` は本アプリの
   メッセージ様式に一致しないため、全異常系がこの候補に上がるが、各 TC の期待結果は §3 の逐語メッセージを
   引用しており曖昧ではない（前提/手順/期待に具体リテラルを保持）。**このクラス全体を根拠付きで棄却**。
2. **`[valid]` ×1** — 「could not run msg_codes (no reg xml)」。
   → **棄却（環境要因・無害）**。監査の `_root_xml` は `parsed/cobol_xml/{main,sub}/MENU00.xml` を探すが、
   本 reg は `parsed/cobol_xml/Sakura/menu/MENU00.xml` レイアウト。手動実行 `msg_codes.py Sakura/menu/MENU00.xml`
   ＝ **0 codes** を確認済みのため、コードカバレッジ判定は「対象コード無し」で完全（見落としは無い）。

**その他の候補は 0 件**: `[wording]`（本文コード漏れ）0、`[fold]`（コード折り畳み）0、`[ids]`（重複 ID）0、
`[fields]`（空フィールド）0、`[auto]`（自動化列不整合）0、`[parity]`（JP/VI 差異）0。
→ 全コード識別子は 備考 のみに配置、本文は業務日本語＋逐語メッセージのみで、監査のコード漏れ検出に
かからないことを機械的に確認。
