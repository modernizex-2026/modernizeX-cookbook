未網羅コードの原因分析

技術的見解: 未網羅メソッドは、業務ロジック実態を明確化するため、技術的性質により4グループ（A, B, D, C）に分類されます。
グループ A — フレームワーク入口 & 異常終了処理
バッチフレームワーク入口とインフラ異常処理

mainProcess() は BatchServiceBase.execute() がランタイム起動時に呼び出す唯一の入口です。UT は各業務メソッドを直接呼ぶため、設計上ここは通過しません。

abort*(), setCompletionCode(), getFileSet() は I/O 障害 / DB 障害の異常終了分岐で、UT では再現不可能です。

グループ B — 業務ロジック本流
複数マスタ同時整合が必要な業務ループ本体

データ整合チェック、マスタ更新、価格/コスト算出、在庫振替など。入力レコードが複数マスタ上で同時整合する場合のみ実行されます。

マルチマスタ整合テストデータの用意は UT の設計範囲を超えるため、System/Integration Test 層で検証します。

グループ D — 自動生成 DAO ラッパー
業務ロジックを持たない自動生成データアクセス層

readX(), writeX(), deleteX(), rewriteX(), startXAtKey(), openXFile() は COBOL FD/SELECT からジェネレータが自動生成する 3〜5 行のシンラッパーで、業務ロジックはありません。

JPA の repository.findById() と同様、独立 UT は不要。設定ミスがあれば呼び出し UT が即失敗するため、自己検出で十分です。

グループ C — 端末対話 (Interactive Terminal)
端末入力フロー — UT では模擬不可能

accept*(), open*Window(), prompt*() は COBOL の ACCEPT FROM TERMINAL/DISPLAY 変換で、実端末からの blocking read です。

端末エミュレータなしに UT で模擬できません。Screen test / manual acceptance test で検証されます。

2. CONVERT-GAP（意図的失敗テスト）

該当なし。GETMSG.cob の MAIN-000 パラグラフと GetmsgService.retrieveMessageByCode() を1行ずつ突き合わせた結果、下記の対応関係に差異は見つからなかった：

  • OPEN INPUT MSGF → FSTS NOT = "00" 分岐 = fileSet.getMsgf().open() → getFileStatus() != "00" 判定（OPEN失敗時に KM-TEXT=KM-CODE, KM-STATUS="99", EXIT PROGRAM）
  • READ MSGF INVALID KEY → isInvalidKey()==true（KM-TEXT=KM-CODE, KM-STATUS="01"）
  • READ MSGF NOT INVALID KEY → isInvalidKey()==false（KM-TEXT=MG-TEXT, KM-STATUS は初期値"00"のまま）
  • CLOSE MSGF → fileSet.getMsgf().close()（OPEN失敗時はREAD/CLOSEをスキップする点も再現済み）

そのため、既存の全テストは COBOL 期待値どおりに成功しており、CONVERT-GAP用の意図的失敗テストは作成していない。

3. カバーできていない残り
  • GetmsgService.retrieveMessageByCode() 内の2行（キー抽出フォールバック用の try { ws.getString("MG-CODE") } catch (Exception _e) {} および try { extractKeyFromCurrentRecord() } catch (Exception _e3) {} の catch節）が未カバー。
  • 理由: これらは生成コード側の防御的フォールバック（rkVal_0 が空の場合の代替キー取得）であり、COBOL側に対応する分岐が存在しないため、通常のテストシナリオでは catch 節に到達しない。ビジネスロジック上のリスクは低いと判断し、追加のモック例外注入テストは見送った。
  • GetmsgJobFlow（Spring Batchの設定/Tasklet/Listener）と GetmsgDatasets／WorkingStorage は本モジュールのJaCoCo計測対象に含まれていない（jacoco.csv に行が出力されない = 設定上の除外、または軽量DIラッパーのため計測不要と判断されている）。Spring配線クラスのため、本skillのユニットテスト対象（Serviceの業務ロジック）としては対象外で問題ない。
4. レビュー時の注意事項
  • 既存の GetmsgServiceTest / GetmsgFieldAccessTest は前回セッションで既に作成済みであり、今回のPhase1調査（COBOL⇔Java突き合わせ）でも内容に問題は見つからなかったため、変更・追加は行っていない。
